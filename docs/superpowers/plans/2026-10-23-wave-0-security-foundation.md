# Wave 0 Security Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the shared server-side security foundation required by Wave 0 without changing quiz, rewards, admin UI, or idea UI behavior.

**Architecture:** Preserve `admin` and `user` as the only JWT roles, but map them to explicit server-only capabilities. Sensitive authorization reads the current user and active session from SQLite, while audit records are append-only and redact/hash request metadata before persistence. Refresh-token rows carry hashed request metadata and revocation/last-seen state; users carry failed-login lockout counters and account/session invalidation state.

**Tech Stack:** Next.js/Auth.js, TypeScript, Drizzle ORM, SQLite/better-sqlite3, Argon2, Node test runner, tsx.

**Spec:** `requirements/ab_ignite_execution_plan.md` and `requirements/ab_ignite_user_stories.md` (CC-02, AD-06, AD-10 security foundation only).

## Global Constraints

- Preserve the existing `admin` and `user` JWT roles; capability checks are additive.
- JWT claims are hints only; sensitive routes revalidate user, role, session, and account state from SQLite.
- Audit records are append-only; IP and user-agent are hashed, and metadata is allowlisted/redacted.
- Privileged mutations require a non-empty reason.
- Do not implement quiz, rewards, admin UI, or idea UI changes.
- Do not rewrite applied migrations; add one sequential migration.

## Review Focus

- Stale admin JWT after DB demotion must be rejected by DB-backed capability checks.
- Revoked or idle sessions must not authorize refresh or sensitive access.
- Lockout counters must reset after a valid login and lock after five failures for fifteen minutes.
- Audit metadata must not persist raw IP, user-agent, token, password, or arbitrary sensitive fields.
- Privileged mutation authorization must reject missing/blank reasons.
